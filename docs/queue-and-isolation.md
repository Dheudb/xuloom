# 子代理排队与系统执行隔离

自动排队与 Windows x64 系统隔离最初随 v0.1.0-beta.11 发布；本页容量默认值已同步到 v0.1.0-beta.13。旧 beta.10 下载包不包含自动排队与系统隔离能力。历史版本的档位配额不能作为当前接入规则。

## 自动排队

Auto / Ultra 默认不设并发数、累计子任务数或共享输出额度，两档只改变委派倾向；Solo 禁止委派。可在 `.xuloom/capabilities.json` 的 `agent_limits` 中显式设置宿主限制；配置字段、优先级与示例见 [协作档位](capabilities.md#协作档位)。

单次 `spawn` 的 `count` 范围仍为 1–10，可再次提交；这是单批传输大小，不是会话总容量。显式并发数为 3 时，一次提交 10 个有效任务会被接纳，空闲槽位启动任务，其余 FIFO 排队，结束一个补上一个。并发占满本身不导致整批拒绝；显式累计配额、共享输出额度或底层宿主队列上限等边界仍可能拒绝调用。

队列默认不设长度上限，不存在默认 1000 项限制。`capacity.limit`、`available` 为 `null` 表示未设置并发上限，`queue_limit=null` 表示未设置队列上限；不能把 `null` 当作零。底层宿主可通过现有 `SubagentTasks` 设置队列上限；该字段不属于 `agent_limits` 配置。字段语义和上层等待方式见 [通用执行接口](framework.md#程序调用当前开发源码)。

排队期间不发起模型请求，也不预留模型输出；真正开始运行时才申请适用的输出预算。设置了有限输出预算时，缺少供应商 usage 的请求仍按预留量保守计入预算，不能把缺失 usage 当作零消耗；这不是精确的供应商金额账单。每次响应默认上限仍为 64,000 tokens，并受模型/API 自身限制。父代理最终汇总等待所有已接纳的关联任务终止，明确区分失败、取消和成功。

完整派发参数和实际 ID 保存在原会话记录中，没有第二套调度数据库。重启后未启动任务显示“等待恢复队列”，可在代理卡片恢复；程序接口是 `await engine.agents("resume_queue", agent_ids=[...])`。已经执行中断的任务不自动重放，需核查副作用后按原恢复机制继续。取消排队任务不会调用模型。

## 执行隔离

审批解决“是否授权执行”；系统隔离解决“执行后能访问什么”，两者独立。默认仍为宿主执行。

- 桌面：输入框 **＋ → 执行隔离 → 工作区系统隔离**，按会话保存，重启保留。
- 非交互 CLI：`xuloom exec "任务" --cwd C:\work\project --sandbox workspace --permission full --json`。
- 交互 CLI：`xuloom --sandbox workspace`。
- Python：`QueryEngine(cwd=workspace, execution_mode="workspace")`。

Windows x64 后端使用 LPAC：唯一临时 Package SID、只读 Python/工具运行时授权、工作目录和私有临时目录写授权，不授予网络能力或 COM 能力。`registryRead` 仅用于 Python 启动所需的注册表访问。Job Object 在子进程恢复执行前绑定，限制进程数量和内存，退出、取消或宿主结束时终止所属进程树。仅继承三个标准流句柄；API Key 等环境变量不传入工具进程。

文件工具在固定的受限工作进程中调用原工具实现；命令及 REPL 的实际用户代码也运行在受限进程。文件缓存、变更事件和写入队列继续复用宿主原有记录。命令完整输出仍由原命令会话存储和分页。

MCP 服务启动/测试、浏览器、LSP、命令 Hook、旧 Bash 与旧后台 Shell 工具尚无受限后端，因此在此模式禁用；模型连接仍由可信宿主完成。隔离不支持的工具会明确拒绝，不能通过“完全访问”绕过。运行中不能切换隔离设置。

工作目录中的文件（包括项目 `.xuloom` 配置）均属于授权工作区。框架运行目录、中央会话存储、用户凭据目录不可与可写工作区重叠，重叠时拒绝启动。系统运行时有只读访问例外；私有临时目录同样可写。工作区中的目录链接不能授权访问原本无权访问的外部文件。

## 当前边界

这是 Windows x64 的首个系统隔离实现，未提供 Linux/macOS 后端；不支持的平台明确失败。部分需要网络初始化、COM 或设备访问的程序可能不能运行，不能据此自动开放权限或降级宿主执行。

每次工具启动要创建隔离身份并设置/撤销文件授权，存在额外开销。普通退出和取消会清理临时身份；若强行杀死负责清理的辅助进程，Windows Job 仍会终止其子进程，但可能遗留不可复用的临时身份/ACL 元数据。它也不代替虚拟机或独立用户账户对抗操作系统漏洞的防护。

清理操作现在检查 ACL 与 AppContainer 删除的返回值；创建授权前，辅助进程会在中央数据目录 `sandbox-cleanup` 保存所属 SID、配置名称及路径，并持有 OS 租约。清理失败保留具体错误，活动日志给出提示，执行隔离设置提供“重试清理权限”。失败清理未解决前不再启动新的隔离工具；原执行结果保留，清理不会重新执行任务。

CLI 可使用 `xuloom sandbox-cleanup --cwd <工作目录> --json` 查看，使用 `--id <记录ID>` 明确重试。恢复会核对工作目录、所属配置名称与由名称派生的真实 SID；活跃租约不能被接管。正常完成、失败、取消和进程意外退出共用这份记录，不按旧 PID 结束进程，也不移除其他账户的权限。

私有临时目录的删除还核对创建时保存的文件身份，拒绝目录链接、被替换的目录及与工作目录重叠的路径。旧记录没有文件身份时，必须先在该目录实际 ACL 中确认属于该 SID 的显式可写授权，再保存身份并清理；无法证明归属就保留目录并显示错误。损坏记录单独显示诊断，不妨碍其他记录查看；恢复入口不会根据损坏内容猜测删除目标。

验证使用本地模型协议替身和真实 Windows 受限进程，不调用远端模型；测试通过不能自动证明所有应用兼容或真实长任务已成熟。

## JiuwenSwarm 调度对照与增量实现

本次静态核对固定在 JiuwenSwarm `a75eccb69c310fc08981b54ec000a63ae08c84e6`，以及其实际锁定的 agent-core `c8c621b22f1ad5da6acee0ceee33778007c06efb`。没有安装该框架或将源码阅读视为真实模型性能验收。

[SwarmFlow 核心算子](https://github.com/openJiuwen-ai/agent-core/blob/c8c621b22f1ad5da6acee0ceee33778007c06efb/openjiuwen/agent_teams/workflow/engine/primitives.py)提供等齐分支的并行汇合、逐项独立推进的流水线和结构路径绑定的调用记录。编排协程不持有实际模型执行的并发许可；命中已完成、签名相符的记录时，读取原结果而非重新发起模型调用。[会话调度器](https://github.com/openJiuwen-ai/jiuwenswarm/blob/a75eccb69c310fc08981b54ec000a63ae08c84e6/jiuwenswarm/runtime/session/work_scheduler.py)则让同一会话串行执行、不同会话并行，并检查会话 generation，属于不同层次的协调。

Xuloom 已按此边界增量实现，使用说明见 [协作组合接口](coordination.md)：

1. 在现有子代理 API 上提供统一的全量汇合及逐项流水线组合方式。现有前台批量执行、文本等待和最终完成保护已有等齐语义；结构化 `wait` 现可显式指定 `wait_for=any/all`，不再把任一结束误当全量汇合。逐项流水线直接关联并推进阶段，减少上层反复转抄 ID 和轮询。
2. 用既有执行记录关联节点、依赖、输入与真实产物，按确定的前置条件推进后续步骤。分工仍由模型或用户工作流决定，Runtime 负责关联和推进，不让模型靠口头宣布阶段完成。
3. 将既有事件投影为阶段／任务树，显示运行、等待前置阶段、失败、取消、完成和待恢复。界面不是第二套完成状态的来源；恢复仍核对原执行回执及输入，不仅靠节点标签复用结果。

上述薄层组合已实现，未增加独立调度服务、技能评分图或自演进服务。Xuloom 继续复用现有原生／外部／SSH 生命周期、持久化、权限与取消入口。对应核心中的部分失败会返回 `None`；Xuloom 的组合层应继续保留结构化失败和原始证据，明确必需步骤失败是否阻塞下游，避免混淆空结果与执行错误。
