## 问题与修复

0.1.18 的版本检查会接受 `null`、布尔、负数或字符串等修订号，有些直到下一次保存才报错。使用临时数据与实际加密回环 SSH 复现：替换控制器恢复后，把本机子代理存档的 `revision` 改为 `null`；后续调用在被拒绝前仍新增一次 SSH 启动和两次本地模型请求。测试没有观察到远端文件写入，不能将请求发生描述为已经造成重复文件副作用。

现在使用现有 `SessionManager` 的同一个解析入口，在保存执行基线前检查 JSON、消息／元数据类型和非负整数修订号。无效文件保留原字节，不触发续跑，不覆盖先前有效的预期版本。旧主会话数组及缺少修订号的正常对象继续恢复。会话 ID 校验复用已有写者锁规则，覆盖读、保存、检查和删除入口。

新明确错误也要求调用方正确清理。桌面端把恢复、写者获取、模型配置与引擎配置纳入同一初始化异常清理；失败时关闭临时引擎，不启动 MCP，不保留写者锁。正式 CLI 继续用现有 `session_conflict` 回执和退出码 `4`，不另加状态或自动修复流程。已加载会话在下一次执行前同样检查存档，没有仅修冷启动。

## 边界

0.1.20 验证时追加的来源校正：上述 0.1.19 成品主测试进程的模块来源核对有效，但“正式 CLI 子进程也从安装目录导入”的表述过强。单独的来源探针确认，继承仓库工作目录时，子进程仍可能优先导入同内容的源码，设置 `PYTHONPATH` 不能消除这个优先级。当前媒体、非交互 CLI 与写者子进程用例已改为自有临时工作目录；补跑时同时核对安装包及子进程来源。0.1.19 的源码与安装资源确已逐字节一致，保留其功能证据，但不再将这些旧 CLI 子进程视为独立、隔离的成品验证。

这次只检查检查点容器结构及修订号，并非所有历史消息、领域结果或外部 CLI 原生日志的完整语义验证，也不提供自动恢复损坏文件。只读历史与执行基线继续分开，不通过查看历史默默重置写者的版本。

Windows 浏览器测试目录清理仍有既有时序敏感；系统级隔离、物理两机、Linux／macOS 原生验收和真实供应商长任务保持各自边界。没有新增运行时依赖、管理器、数据库或提示词，私人 Taiyi Skill 不进入源码和 Release。
