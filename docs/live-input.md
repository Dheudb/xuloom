# 运行中追加指令

桌面主任务执行时，可继续在输入框填写补充要求，按 Enter 或点击“追加指令”。消息先显示“等待当前步骤结束后送达”，送达后成为正常的用户消息，回答继续在其后输出。停止按钮始终保留；未送达的消息可以撤回。

## 实际送达边界

- 先把补充要求保存到当前会话，再确认接收。保存失败不会报告成功。
- 当前模型响应、已经开始的工具操作会先结束；已完成结果保留。尚未开始的旧工具调用返回“未执行”的回执，交给模型根据新要求重新判断。
- 等待子代理结果期间也能接收输入；追加文字不会自动取消或重建现有 worker。
- 正在等待权限审批或用户问题时，仍需处理原交互，或主动停止。追加文字不能代替授权，也不会强制打断任意外部进程。
- 停止、关闭、重启后，未送达消息留在集中会话记录中。显式继续原任务后送达；也可先撤回，再开始新任务。不会因打开历史而自动执行。
- 持续目标允许追加要求，但正式的目标及验收条件不会被悄悄覆盖。要替换目标，先暂停并处理未送达消息，再编辑目标。

这是文字补充入口；执行过程中不能借此替换模型、附件或已加载的 Skills。子代理历史仍由原主会话控制。远端桌面工作区需两端都支持此协议；旧远端保持原有禁用输入行为。

## 程序化 CLI

正式非交互 CLI 可以从管道持续读取 UTF-8 JSONL：

```text
xuloom exec "原始任务" --input-stream --json
```

由调用方通过进程 stdin 写入以下命令，每条一行：

```json
{"type":"input","text":"保留已完成工作，后续优先分析第二种方案","request_id":"5c23d2d9-0c62-47ef-868e-e548a50a0f87"}
{"type":"withdraw","request_id":"5c23d2d9-0c62-47ef-868e-e548a50a0f87"}
{"type":"stop"}
```

`request_id` 可省略，由引擎生成 UUID。重发同一 ID、同一文字可核对尚在队列或当前消息历史中的接收状态；同 ID 不同文字会拒绝。客户端应复用未确认请求的 ID，不把网络重试变成另一条要求。这不是外部副作用的 exactly-once 保证。

输出事件包括 `user_input_queued`、批量 `user_input_applied`、`user_input_withdrawn` 和 `input_error`；最终结果及退出码沿用原执行协议。stdin EOF 只结束输入，不取消任务；任务结束不必等待 stdin 关闭。`--input-stream` 不能同时使用 `-` 读取原始 prompt。

恢复停止的原任务：

```text
xuloom exec --session 会话ID --resume --input-stream --json
```

`--resume` 不接受替换 prompt 或 Skill。普通交互式 TTY 暂未增加运行中行编辑；以上能力面向桌面、非交互输入流和程序 API，不宣称终端界面完全一致。

## 嵌入接口与开销

同一事件循环中的 `engine.queue_input(text, request_id=None)` 返回 `id / text / status`。恢复仍使用 `load_session(id)` 和 `submit_message('', resume=True)`。能力事件通过现有同步 `set_event_handler` 监听；CLI 流事件使用原回执通道。

队列复用现有会话 metadata 和单写者保护，只增加等待事件；没有新数据库、执行器或常驻监督模型。无补充输入时不增加模型请求，也不增加默认提示词。实际追加要求后需要继续请求模型，仍受原权限、模型和运行上限约束。
